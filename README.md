# Dungeon Master

Каркас монорепозиторію для D&D-сайту. Поточна папка `DnD` є коренем проєкту; додаткова вкладена папка `dungeon-master` не потрібна.

## Структура

```text
apps/
  client/
    public/                 Статичні файли
    src/
      app/                  Ініціалізація застосунку, router, провайдери
      pages/                Сторінки маршрутів
        LoginPage/
        RegisterPage/
        CampaignsPage/
        JoinPage/
        DungeonMasterPage/
        PlayerPage/
      components/ui/        Спільні кнопки, поля, діалоги
      features/
        auth/               Інтерфейс авторизації
        campaigns/          Інтерфейс кампаній та запрошень
        room/               Учасники, підключення, пінги
        scenes/             Тестова сцена та токени
      lib/                  HTTP-клієнт, Socket.IO-клієнт
      stores/               Стан клієнта
  server/
    prisma/
      migrations/           Міграції PostgreSQL
    src/
      auth/                 Реєстрація, вхід, сесії
      campaigns/            Кампанії, членство, ролі, запрошення
      scenes/               Сцени та активна сцена кампанії
      tokens/               Позиції токенів та дії DM
      sockets/              Підключення, кімнати, події, присутність
      database/             Клієнт бази та транзакції
      middleware/           Авторизація, обробка помилок
      config/               Перевірка змінних оточення
      lib/                  Допоміжний код сервера
packages/
  shared/
    src/
      types/                Спільні типи даних
      schemas/              Схеми Zod для вхідних даних
      events/               Контракти подій Socket.IO
```

## Межі модулів

- `pages` збирають сторінки з компонентів відповідних `features`.
- Компоненти конкретної функції живуть у її папці `features/<назва>/components`, коли вони з'являться.
- `components/ui` містить лише компоненти загального призначення.
- `shared` не містить секретів, доступу до бази або залежностей від React чи Express.
- Сервер перевіряє сесію, членство та права для HTTP-запитів і socket-подій.
- База зберігає постійний стан; присутність та пінги є тимчасовими.

BattleMap і SceneManager додаватимуться до `features/scenes`; DiceRoller, MusicPlayer та CutscenePlayer отримають власні features, коли почнеться їх реалізація.

## Локальний запуск

Потрібен Node.js 24.14 або новіший у гілці 24 та npm.

```sh
npm ci
npm run dev
```

Клієнт: http://localhost:5173. Сервер: http://localhost:3001.
Vite проксіює `/api` та `/socket.io` на сервер під час розробки.

```sh
npm run typecheck
npm run build
npm run start -w @dnd/server
```

`GET /api/health` повертає HTTP 200 з `{"status":"ok"}` і перевіряє лише роботу сервера, без бази даних.

Встановлені React, React Router, Express, Socket.IO, Zod, Prisma та PostgreSQL-драйвер.

## Реєстрація та вхід

Сторінки `/register` та `/login` працюють із серверною авторизацією. `/campaigns` вимагає входу. Стан користувача відновлюється через `/api/auth/me` після перезавантаження. Вихід відкликає поточну сесію в базі.

## Кампанії та запрошення

- `/campaigns`: створення кампанії й список лише своїх кампаній із ролями.
- `/campaigns/:id`: спільна кімната, роль, учасники онлайн; для DM — створення та відкликання запрошень.
- `/join/:code`: явне підтвердження приєднання. Неавторизований користувач спочатку входить або реєструється, після чого повертається до запрошення.

Запрошення дійсне 7 днів і підходить для кількох гравців. Посилання відображається лише після створення; збережіть його перед виходом зі сторінки. У базі зберігається лише хеш коду. Повторне приєднання не дублює членство й не змінює існуючу роль. Відкликання забороняє нові приєднання, але не видаляє наявних учасників.

Кампанія та членство DM створюються атомарно. Сервер перевіряє сесію, членство й права DM для кожного відповідного маршруту. Email, паролі, сесії та хеші запрошень у відповіді кампанії не потрапляють. Контракт: `apps/server/campaigns-api.md`.

```sh
npm run build
npm run test:campaigns -w @dnd/server
```

Тест створює три тимчасові облікові записи та кампанію в налаштованій базі, перевіряє ролі, доступ, паралельне приєднання та запрошення і видаляє свої дані. Для посилань запрошення використовується `APP_ORIGIN` (локально `http://localhost:5173`); перед хостингом задайте публічну адресу сайту.

Паролі: 12–128 символів, scrypt із випадковою сіллю. Сесії: випадкові 256-бітні токени, лише SHA-256 хеші в базі, строк дії 7 днів. Cookie має HttpOnly, SameSite=Lax та Secure у production. Спроби входу/реєстрації обмежені 30 запитами на IP за 15 хвилин на один серверний процес. Для кількох серверів потрібне спільне сховище лімітів. Перевірка email і відновлення пароля ще не реалізовані.

У production задайте `NODE_ENV=production`. На Render адреса береться автоматично з `RENDER_EXTERNAL_URL`; для власного домену задайте `APP_ORIGIN=https://ваша-адреса`. Один Node.js-сервер віддає React, API та Socket.IO через спільну HTTPS-адресу. Локально працює проксі Vite. Інструкція розгортання: [DEPLOYMENT.md](DEPLOYMENT.md).

Контракт маршрутів: `apps/server/auth-api.md`.

```sh
npm run build
npm run test:auth -w @dnd/server
```

Тест запускає сервер на порту 3102, перевіряє HTTP-сценарії з реальною базою та видаляє лише створеного ним випадкового тестового користувача разом із сесіями. Не запускайте цей тест проти чужої бази без дозволу.

## База даних

Prisma використовує PostgreSQL через `@prisma/adapter-pg`, максимум 5 з'єднань на сервер. Реальні секрети зберігаються в ігнорованому `apps/server/.env`, приклад — `.env.example`. Не вимикайте перевірку TLS-сертифіката.

Моделі: User, Session, Campaign, CampaignMember, Invite. Сесії та запрошення містять лише хеші токенів. Авторизація нормалізує email до нижнього регістру. Створення кампанії та її DM виконується атомарно; перевірка прав DM належить серверній логіці.

```sh
npm run db:generate -w @dnd/server
npm run db:deploy -w @dnd/server
npm run db:status -w @dnd/server
npm run db:check -w @dnd/server
```

`db:deploy` застосовує наявні міграції без скидання даних. Першу міграцію створено через `prisma migrate diff --from-empty`; майбутні міграції потрібно створювати від поточної схеми, перевіряти SQL та зберігати в Git. Не редагуйте застосовані міграції.

`db:check` перевіряє запис, читання та зв'язки всіх п'яти моделей у транзакції, яка навмисно відкочується. `GET /api/ready` перевіряє доступ до таблиці Campaign: HTTP 200 при успіху, HTTP 503 при недоступності бази. Деталі підключення у відповіді не повертаються.

Prisma CLI завантажує `.env` сервера та використовує `DIRECT_URL`, якщо він заданий, інакше `DATABASE_URL`. Згенерований клієнт не зберігається в Git і створюється перед `dev` та `build`. Перед окремим `typecheck` у чистому checkout виконайте `db:generate`.

## Кімната в реальному часі

Сторінка кампанії автоматично підключається до її Socket.IO-кімнати через cookie-сесію. Список учасників та їхня присутність оновлюються без перезавантаження. Кілька вкладок одного користувача рахуються як один онлайн-учасник.

Тестове поле містить дві сцени з одним токеном на кожній. DM натискає на поле (або вводить координати), щоб пересунути токен, та перемикає сцени. Player натисканням надсилає тимчасовий пінг — остаточну позицію визначає DM. Сцена, позиції та версія зберігаються в PostgreSQL; пінги та присутність є тимчасовими.

Після втрати мережі клієнт автоматично перепідключається й отримує актуальний стан. Дії офлайн заблоковані. Вихід відкликає сесію та відключає її sockets. Після відмови в доступі потрібен повторний вхід або ручне перепідключення.

```sh
npm run build
npm run test:rooms -w @dnd/server
```

Контракт і обмеження: `apps/server/rooms-api.md`. Перевірка використовує DM та шістьох гравців як локальні Socket.IO-клієнти з реальною базою, очищає свої тестові дані. Перевірка різних ПК через інтернет потребує публічного хостингу.

Підтримується один backend-процес. Для кількох серверів знадобляться спільний adapter Socket.IO, присутність, відкликання сесій та впорядкування подій. Shared-пакет збирається перед root-командами `dev`, `build`, `typecheck`; контракти експортуються з `packages/shared/dist`.
